# Laporan Praktikum Modul 4
## Normalisasi dan Skema Relasional

## 1. UNF (Unnormalized Form)

Pada tahap UNF, data penjualan Kopma masih berada dalam satu relasi
besar. Data transaksi dan data barang masih digabungkan dalam satu
struktur dan terdapat grup data barang yang berulang.

### Relasi NOTA_UNF

NOTA_UNF (
no_nota_penjualan,
tanggal_penjualan,
no_anggota,
nama_anggota,
no_hp_anggota,
id_petugas,
nama_petugas,
jabatan,
{
kode_barang,
nama_barang,
satuan,
jumlah,
harga_satuan
},
id_pembayaran,
tanggal_bayar,
metode_bayar,
total_penjualan
)

Tanda `{}` menunjukkan grup berulang karena satu nota dapat memiliki
lebih dari satu barang.

### Contoh

Satu nota dapat berisi beberapa barang. Misalnya:

| no_nota_penjualan | no_anggota | kode_barang | nama_barang | jumlah | harga_satuan |
|---|---|---|---|---:|---:|
| PJ-001 | A-0457 | BRG001 | Buku Tulis | 2 | 5000 |
| PJ-001 | A-0457 | BRG002 | Pulpen | 3 | 3000 |

Data tersebut masih berada dalam satu transaksi yang sama sehingga
perlu dinormalisasi.

---

## 2. 1NF (First Normal Form)

Pada tahap 1NF, grup berulang pada NOTA_UNF dihilangkan.
Setiap nilai data harus bersifat atomik dan setiap barang dalam satu
nota dicatat sebagai baris yang berbeda.

Kunci primer sementara menggunakan gabungan:

(no_nota_penjualan, kode_barang)

### Relasi NOTA_1NF

NOTA_1NF (
no_nota_penjualan,
kode_barang,
tanggal_penjualan,
no_anggota,
nama_anggota,
no_hp_anggota,
id_petugas,
nama_petugas,
jabatan,
nama_barang,
satuan,
jumlah,
harga_satuan,
id_pembayaran,
tanggal_bayar,
metode_bayar,
total_penjualan
)

### Contoh Data 1NF

| no_nota_penjualan | kode_barang | nama_barang | jumlah | harga_satuan |
|---|---|---|---:|---:|
| PJ-001 | BRG001 | Buku Tulis | 2 | 5000 |
| PJ-001 | BRG002 | Pulpen | 3 | 3000 |

Pada tahap ini, tidak ada lagi grup berulang dalam satu atribut.
Namun masih terdapat ketergantungan sebagian terhadap kunci komposit.
Oleh karena itu data perlu dilanjutkan ke tahap 2NF.

---

## 3. 2NF (Second Normal Form)

Pada tahap 2NF, ketergantungan sebagian terhadap kunci komposit
dihilangkan dengan memisahkan data yang bergantung pada masing-masing
entitas.

### Relasi PENJUALAN

PENJUALAN (
no_nota_penjualan,
tanggal_penjualan,
no_anggota,
id_petugas,
id_pembayaran,
tanggal_bayar,
metode_bayar,
total_penjualan
)

### Relasi BARANG

BARANG (
kode_barang,
nama_barang,
satuan,
harga_jual,
stok_barang
)

### Relasi DETAIL_PENJUALAN

DETAIL_PENJUALAN (
no_nota_penjualan,
kode_barang,
jumlah,
harga_satuan
)

### Relasi ANGGOTA

ANGGOTA (
no_anggota,
nim_anggota,
nama_anggota,
no_hp_anggota
)

### Relasi PETUGAS

PETUGAS (
id_petugas,
nama_petugas,
jabatan
)

### Penjelasan

Data anggota dipisahkan karena informasi anggota bergantung pada
no_anggota. Data barang dipisahkan karena informasi barang bergantung
pada kode_barang.

Data jumlah barang yang dibeli bergantung pada kombinasi
no_nota_penjualan dan kode_barang sehingga disimpan pada
DETAIL_PENJUALAN.

Dengan pemisahan tersebut, ketergantungan sebagian terhadap kunci
komposit dapat dihilangkan.

---

## 4. Functional Dependency (FD)

Functional Dependency digunakan untuk menunjukkan hubungan
ketergantungan antaratribut.

Berdasarkan aturan bisnis Kopma, beberapa FD yang dapat ditentukan
adalah:

### FD Entitas Anggota

no_anggota → nim_anggota, nama_anggota, no_hp_anggota

Artinya, satu nomor anggota menentukan data anggota tersebut.

### FD Entitas Barang

kode_barang → nama_barang, satuan, harga_jual, stok_barang

Artinya, satu kode barang menentukan informasi barang.

### FD Entitas Petugas

id_petugas → nama_petugas, jabatan

Artinya, satu ID petugas menentukan nama dan jabatan petugas.

### FD Penjualan

no_nota_penjualan → tanggal_penjualan, no_anggota, id_petugas,
id_pembayaran, tanggal_bayar, metode_bayar, total_penjualan

Artinya, satu nomor nota menentukan informasi utama transaksi.

### FD Detail Penjualan

(no_nota_penjualan, kode_barang) → jumlah, harga_satuan

Artinya, kombinasi nomor nota dan kode barang menentukan jumlah
dan harga barang pada transaksi tersebut.

---

## 5. 3NF (Third Normal Form)

Pada tahap 3NF, setiap atribut non-kunci harus bergantung langsung
pada kunci primer dan tidak boleh terdapat ketergantungan transitif.

Struktur tabel hasil normalisasi adalah sebagai berikut.

### Tabel ANGGOTA

| Atribut | Keterangan |
|---|---|
| no_anggota | Primary Key |
| nim_anggota | NIM anggota |
| nama_anggota | Nama anggota |
| no_hp_anggota | Nomor HP anggota |

### Tabel BARANG

| Atribut | Keterangan |
|---|---|
| kode_barang | Primary Key |
| nama_barang | Nama barang |
| satuan | Satuan barang |
| harga_jual | Harga jual |
| stok_barang | Stok barang |

### Tabel PETUGAS

| Atribut | Keterangan |
|---|---|
| id_petugas | Primary Key |
| nama_petugas | Nama petugas |
| jabatan | Jabatan petugas |

### Tabel PENJUALAN

| Atribut | Keterangan |
|---|---|
| no_nota_penjualan | Primary Key |
| tanggal_penjualan | Tanggal transaksi |
| no_anggota | Foreign Key |
| id_petugas | Foreign Key |
| id_pembayaran | Foreign Key |
| tanggal_bayar | Tanggal pembayaran |
| metode_bayar | Metode pembayaran |
| total_penjualan | Total transaksi |

### Tabel DETAIL_PENJUALAN

| Atribut | Keterangan |
|---|---|
| no_nota_penjualan | Primary Key dan Foreign Key |
| kode_barang | Primary Key dan Foreign Key |
| jumlah | Jumlah barang |
| harga_satuan | Harga saat transaksi |

Pada struktur 3NF, data anggota, barang, dan petugas tidak lagi
diulang pada setiap transaksi. Setiap atribut non-kunci bergantung
langsung pada primary key tabelnya.

---

## 6. BCNF (Boyce-Codd Normal Form)

BCNF diperiksa dengan memastikan setiap determinan pada functional
dependency merupakan superkey.

### Pemeriksaan

1. no_anggota → nim_anggota, nama_anggota, no_hp_anggota
   - Determinan: no_anggota
   - no_anggota merupakan primary key pada ANGGOTA.
   - Memenuhi BCNF.

2. kode_barang → nama_barang, satuan, harga_jual, stok_barang
   - Determinan: kode_barang
   - kode_barang merupakan primary key pada BARANG.
   - Memenuhi BCNF.

3. id_petugas → nama_petugas, jabatan
   - Determinan: id_petugas
   - id_petugas merupakan primary key pada PETUGAS.
   - Memenuhi BCNF.

4. no_nota_penjualan → atribut transaksi
   - Determinan: no_nota_penjualan
   - no_nota_penjualan merupakan primary key pada PENJUALAN.
   - Memenuhi BCNF.

5. (no_nota_penjualan, kode_barang) → jumlah, harga_satuan
   - Determinan merupakan primary key pada DETAIL_PENJUALAN.
   - Memenuhi BCNF.

Berdasarkan functional dependency tersebut, relasi hasil normalisasi
dapat dinyatakan memenuhi BCNF.

---

## 7. Nilai Turunan dan Atribut yang Disimpan

Beberapa nilai dapat dihitung dari data transaksi sehingga tidak
selalu perlu disimpan sebagai atribut dasar.

### Total Penjualan

Total penjualan dapat dihitung dari:

total_penjualan =
jumlah × harga_satuan

untuk setiap detail barang, kemudian seluruh detail dalam satu nota
dijumlahkan.

Namun, berdasarkan kebutuhan data Kopma, total_penjualan sudah
didefinisikan sebagai elemen data pada entitas Penjualan. Oleh karena
itu atribut tersebut dapat tetap disimpan untuk kebutuhan pencatatan
dan pelaporan transaksi.

### Stok Barang

Stok barang merupakan jumlah barang yang tersedia. Nilainya dapat
berubah setelah transaksi penjualan.

Pada kebutuhan data Kopma, stok_barang memang termasuk elemen data
Barang dan digunakan untuk pengelolaan serta pelaporan stok.

---

## 8. Perbandingan Hasil Normalisasi

| Tahap | Kondisi |
|---|---|
| UNF | Data masih tergabung dan terdapat grup barang berulang |
| 1NF | Grup berulang dihilangkan dan data dibuat atomik |
| 2NF | Ketergantungan sebagian terhadap kunci komposit dihilangkan |
| 3NF | Ketergantungan transitif dihilangkan |
| BCNF | Setiap determinan merupakan superkey |

---

## 9. Kesimpulan

Proses normalisasi dilakukan untuk mengurangi redundansi data dan
mencegah terjadinya masalah saat data ditambah, diubah, atau dihapus.

Pada proyek Kopma, proses dimulai dari satu relasi UNF yang masih
menggabungkan data anggota, transaksi, barang, pembayaran, dan
petugas. Selanjutnya data diubah menjadi 1NF dengan menghilangkan
grup berulang.

Pada tahap 2NF, data dipisahkan berdasarkan ketergantungannya sehingga
terbentuk relasi ANGGOTA, BARANG, PETUGAS, PENJUALAN, dan
DETAIL_PENJUALAN.

Tahap 3NF memastikan tidak terdapat ketergantungan transitif pada
atribut non-kunci. Setelah pemeriksaan functional dependency,
struktur relasi yang dihasilkan juga memenuhi kondisi BCNF.

Hasil akhir normalisasi memberikan struktur data yang lebih teratur,
mengurangi pengulangan data, dan dapat digunakan sebagai dasar
pembuatan skema relasional pada tahap berikutnya.
